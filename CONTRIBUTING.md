# Как внести вклад

Спасибо за интерес к БАР. Проект открыт для исправлений, новых языков,
улучшений анализа, интерфейса, документации и self-hosted-инфраструктуры.

## Перед началом

1. Проверьте существующие issues, чтобы не дублировать обсуждение.
2. Для существенного изменения сначала создайте issue с задачей, ожидаемым
   результатом и возможными компромиссами.
3. Уязвимости не публикуйте в обычных issues — используйте процесс из
   [SECURITY.md](SECURITY.md).

## Локальная разработка

Требуется Node.js `>=22.13.0`.

```bash
npm ci
cp env.example .dev.vars
npm run dev
```

Реальные XMLRiver и Firecrawl credentials не нужны для большинства unit-тестов.
Никогда не добавляйте ключи, содержимое `.env*`, пользовательские страницы или
полные production-логи в commit и pull request.

Для изменений семантических связей создайте Python 3.12 venv и установите
`services/triplets-symbolic/requirements-spacy.txt`. Поставляемый spaCy-контур
поддерживает русский и английский; новый язык должен сопровождаться моделью,
тестовым корпусом и описанием ограничений.

## Принципы изменений

- Сохраняйте основной анализ работоспособным без spaCy, Firecrawl и LLM.
- Не отправляйте данные внешнему сервису без явной необходимости и настройки
  оператора.
- Любой ввод страниц, snapshots и внешних API считайте недоверенным.
- Не ослабляйте ограничения SSRF, размера ответа и очистку секретов в ошибках.
- Делайте метрики и рекомендации детерминированными и покрывайте изменение
  небольшим воспроизводимым тестом.
- Обновляйте README и `env.example`, если меняется пользовательская настройка.
- Не добавляйте скрытую телеметрию, водяные знаки или ограничения, несовместимые
  с MIT.

## Проверки

Перед pull request выполните:

```bash
npm run check
```

Для Python-кода дополнительно проверьте синтаксис и выполните соответствующий
fixture/smoke-прогон из `services/triplets-symbolic/README.md`. Если часть проверок
невозможно запустить локально, явно укажите это в pull request.

## Pull request

Хороший pull request:

- решает одну связанную задачу;
- объясняет проблему и выбранный подход;
- перечисляет пользовательские изменения и риски;
- содержит тесты либо объяснение, почему они не нужны;
- отмечает breaking changes и изменения конфигурации;
- не смешивает автоматическое форматирование с функциональной правкой;
- не включает сгенерированные модели, `dist`, локальные результаты и секреты.

Maintainer может попросить разделить слишком большой pull request или добавить
fixture, документацию и проверку обратной совместимости.
